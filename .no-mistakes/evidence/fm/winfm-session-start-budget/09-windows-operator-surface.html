Windows session start: the budget, and what a truncation now names

Captured on the real Windows box the defect lives on — Windows 11 build 10.0.26200, MINGW64_NT-10.0-26200, bash 5.2.37, 22 logical cores — running bin/fm-session-start.sh against a brand-new home with no tasks, no projects and an absent backlog. This is the operator's own terminal surface, unedited.

1. The digest completes, and the platform default is what bounds it

FM_SESSION_START_TIMEOUT unset, box idle. 68,972 ms against the 300s Windows arm — 23% of the bound. Under the old portable 120s it was 72s, already 60% of it. The wake-queue record seeded before the run is delivered, and WAKE_ACK_REQUIRED is emitted, so the drain is not lost.

2. Under ordinary load: 191.6s, which the old 120s bound could not have survived

Same empty home, 16 fork-heavy competitors. The run exceeds the old bound by 71s — it would have truncated and lost the drain, the supervision instructions, the fleet state, the network checks and the whole context digest. At 300s it completes and delivers all of them.

3. A truncation now names the stage it died in

Forced with FM_SESSION_START_TIMEOUT=55, which lands inside the wake-queue stage — the exact stage the reported defect died in. The banner names it, lists precisely the stages that never ran, and attributes the elapsed time per stage. Note WAKE QUEUE printing its header before it had produced any output: headers are emitted as a stage BEGINS.
